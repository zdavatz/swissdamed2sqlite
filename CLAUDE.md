# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Single-binary Rust CLI that downloads swissdamed UDI (Unique Device Identification) data, actors, and mandates from `swissdamed.ch` and exports as CSV and/or SQLite. Output files are date-stamped and organized into `csv/` and `db/` subdirectories (e.g., `csv/swissdamed_25.02.2026.csv`, `db/actors_25.02.2026.db`). Exception: the MiGeL match DB is written to a fixed `db/swissdamed_migel.db` (overwritten each run, not one file per day); `output_db_fixed()` in `src/export.rs` builds the non-dated path and `migel_stats::find_latest_dbs` recognizes both the fixed name and legacy dated `swissdamed_migel_*.db` files.

## Configuration

Sensitive defaults (scp target, Google Drive credentials) are stored in `config.toml`, which is gitignored. Before building for the first time, copy the sample:

```bash
cp config.sample.toml config.toml
# then edit config.toml and fill in real values
```

CLI arguments always override `config.toml`. If a required value is missing from both, the app shows an error dialog and exits. `config.sample.toml` is committed and contains empty-string placeholders; `config.toml` is gitignored and holds real credentials. The release and CI workflows copy `config.sample.toml → config.toml` automatically before building.

**Credential files live in `~/.config/swissdamed2sqlite/`** (dir 0700, files 0600): `linkedin_credentials.json`, `linkedin_token.json`, `twitter_credentials.json`, and the Google service-account `.p12` (referenced by `gdrive_key`). They used to sit in the repo directory — the `.p12` was world-readable at 0644 and was NOT gitignored, only untracked, so a `git add -A` would have committed it. `.gitignore` now also covers `*.p12`, `*.pem`, `*-key.json`. See `src/credentials.rs` for the lookup order.

## Build & Run

```bash
cp config.sample.toml config.toml  # first time only
cargo build              # debug build
cargo build --release    # release build
cargo run -- --csv --sqlite          # download and output both formats
cargo run -- --csv                   # CSV only
cargo run -- --sqlite                # SQLite only
cargo run -- -f data.json --sqlite   # load from local JSON instead of downloading
cargo run -- --sqlite --deploy       # build SQLite and scp to remote server
cargo run -- --diff old.csv new.csv  # diff two CSVs, output to diff/ folder
cargo run -- --actors                # download actors (CSV + SQLite)
cargo run -- --mandates              # download mandates (CSV + SQLite)
cargo run -- --actors --mandates     # download both
cargo run -- --ar-mandates           # join AR actors with their mandates
cargo run -- --ch-rep                # CH-REP only companies (only AR/IM, no MF/PR)
cargo run -- --ch-rep-mandates       # CH-REP companies ranked by mandate count
cargo run -- --ch-rep-mandates --ar-only  # AR-only CH-REPs ranked by mandate count
cargo run -- --migel                 # match UDI devices to MiGeL codes
cargo run -- --migel --deploy        # match and deploy to remote server
cargo run -- --migel --linkedin      # match + generate PNG + publish PNG to LinkedIn
cargo run -- --migel --twitter       # match + generate PNG + publish PNG to X / Twitter
cargo run -- --migel --linkedin --twitter  # publish to both
cargo run -- --migel-stats           # re-render stats PNG from latest DBs (no download)
cargo run -- --migel-stats --linkedin  # re-render PNG and publish to LinkedIn
cargo run -- --migel-stats --twitter   # re-render PNG and publish to X / Twitter
cargo run -- --linkedin-delete 'https://www.linkedin.com/feed/update/urn:li:share:123/'  # delete a LinkedIn post (URN or full URL)
cargo run -- --sigvaris-shop         # scrape shop.sigvaris.com → GTIN→MiGeL override DB
cargo run -- --lookup-chrn CHRN-AR-20000807  # find all SRNs for a given CHRN
cargo run -- --company-ranking               # rank companies by product count
cargo run -- --unique-srns                   # export all unique SRNs with manufacturer + mandate holder
cargo run -- --details --details-limit 500   # per-device detail enrichment (POC: 500 devices)
cargo run -- --details --details-limit 0 --details-threads 32  # full detail rebuild (overwrites DB, all ~153k udiDis)
cargo run -- --details-update                 # incremental: fetch only new/changed udiDis, append to latest DB
cargo run -- --migel --skip-details           # --migel runs the incremental details update by default; opt out with --skip-details
cargo run -- --triage                        # classify public vs professional in latest udi_details DB (no download)
cargo run -- --status-pdf                     # render one-page A4 status PDF (+ nomenclature legend w/ links) from latest udi_details DB
cargo run -- --csv --gdrive --gdrive-sub user@domain.com  # upload CSV to Google Drive
cargo run -- --company-ranking --mailto "a@gs1.ch,b@gs1.ch" --mail-subject "Subject" --gdrive-sub user@domain.com  # email CSV
```

`cargo test` runs the golden-set regression test (`migel::tests::golden_set`): ~700 rows in `tests/fixtures/golden_set.tsv` (genuine-match exemplars per company × code family, every verified FP cluster as expected-NONE, the excluded-company list, deliberate never-match exemplars, forced-match pins) evaluated against the pinned MiGeL XLSX in `tests/fixtures/migel.xlsx`. Run it after ANY matcher rule change; if a delta is intended, verify each failing row and regenerate the fixture from a verified run. A second test (`migel_stats::tests::render_worst_case_layout`) smoke-renders the stats PNG with a worst-case layout (more legend entries than palette colors, over-long category names); set `MIGEL_STATS_TEST_PNG=/path/out.png` to inspect its output visually. No linter/formatter configuration — use `cargo fmt` and `cargo clippy`.

## Architecture

Modular Rust binary. `src/main.rs` holds CLI parsing (`Args`), `app_data_dir()`, config loading, error-dialog plumbing, and dispatch into the modules below:

- `src/credentials.rs` — where credential files live. `find(name)` resolves a credential path in the order `$SWISSDAMED_CREDENTIALS_DIR` → `~/.config/swissdamed2sqlite` → cwd → `$HOME`; `dir()` returns the preferred directory, `ensure_dir()` creates it mode 0700, `searched_locations()` feeds "not found" errors so they name the expected place. The cwd/`$HOME` fallbacks are legacy and deliberately last — they keep installs working that share the LinkedIn files with `li_push_rs`. An exported-but-EMPTY `$SWISSDAMED_CREDENTIALS_DIR` must fall through rather than resolve to `""` (that would make every credential path relative to cwd); there is a test pinning this. Resolves paths only — the files stay plaintext, the 0700/0600 permissions are obscurity, not encryption. Consumed by `linkedin.rs` and `twitter.rs`; the `.p12` path comes from `config.toml`'s `gdrive_key` instead.
- `src/data.rs` — JSON → header/row flattening (`collect_headers`, `build_rows`, `collect_flat_headers`, `build_flat_rows`). **Packaging hierarchy (05.10.2026):** `build_rows` only expands `udiDis[]`, so the main `swissdamed` table holds base-unit UDI-DIs. `build_package_rows` flattens each UDI-DI's `packageUdiDis[]` and the nested `children[]` (next-outer level) into one row per package level, written by the UDI export as a second table **`swissdamed_packages`** in the same dated DB (`export::append_sqlite_table`, indexes on `udiDiCode` + `packageUdiDiCode`) and as `csv/swissdamed_packages_DD.MM.YYYY.csv`. Columns: `basicUdiDiCode, udiDiCode, packageUdiDiCode, parentPackageUdiDiCode, level, numberOfItems, totalNumberOfDevices, marketStatus, lastModifiedAt, id, applicableLegislation` (`level` 1 = package directly around the base unit; `parentPackageUdiDiCode` empty on level 1). NB the package code field is `packageUdiDiCode`, not `udiDiCode`, and deeper levels sit under `children`, not `packageUdiDis`. 05.10.2026: 260'006 UDI-DIs + 15'525 package UDI-DIs (level 1: 13'709, level 2: 1'781, level 3: 35) = 275'531 distinct codes.
- `src/download.rs` — paginated POSTs to the swissdamed.ch API (`download_all_pages*`, `load_json_file`).
- `src/details.rs` — `--details` mode: per-device detail enrichment. The slim list endpoint (`POST /public/udi/basic-udis`) carries no intended-purpose/EMDN/characteristic data; the full regulated attribute set lives behind `GET /public/udi/udi-dis/{udiDiId}/details` where `{udiDiId}` is the nested `udiDis[].id` UUID (NOT the `udiDiCode`/GTIN). Public but behind a load-balancer sticky-session cookie (`sm-cookie-be`): first request `302`+Set-Cookie → same URL → `200`; the shared cookie-store client follows it transparently. Pages the list to collect udiDi refs (`--details-limit N`, 0 = all ~193k; ratio ~7.5 udiDis/basic-UDI), then fetches details in parallel via a rayon pool (`--details-threads`, default 32, `map_init` gives each worker its own client/cookie affinity, 3 retries). API tolerates parallelism well (~188 req/s measured, no 429; full run ~20 min). **Incremental + daily hook:** `--migel` refreshes the details DB by default (opt out `--skip-details`), reusing its own UDI download — `update_details()` carries the latest `udi_details_*.db` forward into today's date-stamped file, then fetches details only for NEW or CHANGED udiDis (change key = `udiDis[].lastModifiedAt`), replaces changed rows and drops delisted ones (only successfully-refetched ids are deleted-then-inserted, so a fetch failure never loses a row). `ensure_schema()` migrates older DBs via `ALTER TABLE ADD COLUMN`, and a one-time SQL backfill fills `lastModifiedAt` from `rawJson` so change-detection covers the whole corpus. New rows are triage-classified inline (via `classify()` in `build_row`); run `--triage` to re-classify all after a rule change. `--details-update` runs the same incremental pass standalone (downloads the list); `--details` still does a full overwrite rebuild. Transient `request error for <uuid>` lines are normal on a big run (88 of 2,923 on 27.08.2026) and self-heal: a failed id is never written, so it stays *new* (or keeps its stale `lastModifiedAt`) and the next `--details-update` refetches exactly those — re-running it right away is the fix, no flag needed. Writes `db/udi_details_DD.MM.YYYY.db` table `udi_details` (35 TEXT cols): identity (+`lastModifiedAt`) + intended-purpose (`emdnCode`/`emdnTerm` = EMDN nomenclature ≈ Zweckbestimmung, ~100% coverage; `additionalDescription`; `eudamedBasicUdiUri`) + MDR/IVD yes/no characteristics (implantable/reusable/sterile/measuringFunction/… ; selfTesting/nearPatientTesting/professionalTesting/companionDiagnostics/reagent/instrument/kit/…) + **`rawJson`** = the complete verbatim detail response (verified deep-equal, lossless catch-all: 104 of 133 key-paths — criticalWarnings, storageHandlingConditions, cmrSubstances, clinicalSizes, packages, ownerInfo AR/MF, modelName, referenceNumber, … — live only here, queryable via SQLite `json_extract`).
  `load_udis_with_emdn_prefix()` (10.11.2026) feeds the MiGeL EMDN layer: udiDiCodes with EMDN `Y0618`/`Y0624` (limb prostheses) from the newest details DB → `24.03.01.00.1`.
- `src/triage.rs` — `--triage` mode + `classify()`: labels each `udi_details` row `intendedUser` ∈ {professional, public, review} + `iuConfidence` {high/medium/low} + `iuReason`. **Decision-support, NOT a compliance determination.** swissdamed exposes no structured intended-user field for MDR (95% of corpus); only IVD carries `selfTesting`/`nearPatientTesting`/`professionalTesting`. Two questions are answered, kept separate by confidence: **intended-user** (who is it *for*) via high/medium `public` — only from a structured IVD self-testing signal, **MiGeL membership** (KLV Art. 20 lay-use), or an explicit lay-use text statement (asymmetric: a false high/medium `public` = selling a professional-only device = breach; a false `professional` = only a lost sale) — and **shop-sellability** (may it be *sold* to the public under MepV, default yes unless restricted) via `public/low` (the `PUBLIC_EMDN_CODES` curated allow-list + the TIER-7 presumptive-consumer sweep). `public/low` is a restriction-not-found presumption, always verify IFU; the high/medium public tiers remain the conservative intended-user signals. `classify(detail, migel_code)` takes the device's matched MiGeL position; `load_migel_matches()` builds the `udiDiCode→migel_code` map from `db/swissdamed_migel.db` (else newest legacy `swissdamed_migel_*.db`; best-effort, empty map if absent). Rule order (first match wins): (1) professional/high = AIMDD ∪ implantable ∪ CLASS_III/D — **but a MiGeL match here is a genuine conflict** (e.g. Omnipod 5: CLASS_III yet a real MiGeL home device) → routed to `review/low` with a "MiGeL-listed … but high-risk — verify" note, never silently public/professional; (2) public/high = IVD selfTesting ∪ risk class IVD_DEVICES_SELF_TESTING; (3) professional/medium = IVD professional/near-patient testing (a structured prof-testing field outranks the MiGeL lean); (4) **public/medium = MiGeL match** → KLV Art. 20 Selbstanwendung (legally-anchored lay-use, outranks the noisy free text below; still a lean, not proof — verify against IFU); (4b) **public/low = curated consumer EMDN leaf codes** `PUBLIC_EMDN_CODES` (`V0807`/`V08030102`/`V0811` = anti-decubitus mattresses/cushions/protectors — Class I, freely sellable, no MepV Abgabe restriction, but NOT in MiGeL so KLV Art. 20 can't reach them; a documented maintainer determination — **specific leaf codes only, never a bare category letter**, so false-public stays near-impossible); (5) medium text phrases (EN/DE/FR/IT prof/lay); (6) professional/low = EMDN professional categories `EMDN_PROFESSIONAL_CATS` = L/K/C/G/H/J/S/B/D/P/**Z**/**A** (surgical/interventional/sterilisation/blood-transfusion/device-disinfectants/implant-prosthetics/healthcare-equipment — exclusion-only, asymmetric-safe; F deliberately excluded — home dialysis). **Z (added 28.08.2026) is the one category that is not single-sided**: EMDN files home respiratory therapy, insulin pumps and glucose meters as "equipment" alongside operating tables and scialytic lamps, so 999 of its 18,425 rows carry a MiGeL match. Those are already safe (TIER 4 outranks TIER 6), but their *unmatched* siblings would be wrongly asserted professional — hence `EMDN_PROFESSIONAL_EXEMPT_CODES`, 16 leaf prefixes (CPAP `Z12030102`, home/portable ventilators, O2 concentrators + gas-pipeline regulators, aerosol/nebulisers, peak-flow spirometers — **not** `Z1215` wholesale, which also holds clinical spirometers and body plethysmographs; blood-sugar monitoring `Z12040115` + insulin microinfusors `Z12040216` — **not** `Z120401` wholesale, which also holds dermatoscopes and Holter systems; pulse oximeters, NIBP gauges, breast pumps, wound-treatment equipment). Every prefix is evidence-derived — a leaf where the corpus actually holds a MiGeL match — and an exempt row is merely handed on to TIER 7, so the list can only ever *withhold* a professional assertion, never manufacture a public one. **A (added 28.08.2026) is the same shape as Z**: EMDN files the whole ostomy / urine-bag / pen-needle business under "administration, withdrawal and collection" right next to hospital IV hardware (652 of 4,003 A rows hold a MiGeL match), so A is likewise category-excluded plus exempted at leaf level — `A10` (ostomy, whole branch, MiGeL 29.01), `A06030301`/`A06030399`/`A0680` (urine bags + leg-bag accessories, MiGeL 15.14/15.15), `A0101010201`/`A0101010202` (pen needles, MiGeL 03.07.09), `A020102` (disposable infusion/irrigation syringes, MiGeL 03.07.10.10) and the three home-enteral-nutrition leaves `A030403`/`A03010302`/`A080101` (a maintainer call — tube feed is reimbursed as Spezialnahrung, so no MiGeL evidence exists, but it is unambiguously patient-run). Note A stays in `EMDN_CONSUMER_LEAN_CATS` **as well**: TIER 6 strips the clinical bulk, and what the exemption lets through to TIER 7 is exactly the consumer business that presumption is for. **Q01 (dental, added 16.10.2026, maintainer decision)** sits in a separate `EMDN_PROFESSIONAL_PREFIXES` list because the parent category Q is *not* single-sided: Q02 ophthalmic holds contact lenses and lens care (242 MiGeL matches) and Q03 ENT nasal saline and ear devices, while Q01 has 36,020 rows and zero MiGeL matches — even its oral-hygiene leaf Q019003 is labelled "for professional use". It moved exactly 27,156 rows from review/low (Ormco, American Orthodontics, Polident lab materials) and 4,745 from public/low (MegaGen implant parts, impression devices, articulation papers) into professional/low and touched nothing else, as predicted in SQL beforehand; (7) **presumptive consumer (MepV shop-sellability default)** = survived every professional gate above + low-risk MDR/MDD → public/low "sellable under MepV, no Abgabe restriction found, verify IFU": **CLASS_I broad** (lowest MDR risk; professional Class I = reusable surgical instruments already excluded via EMDN L/K), **CLASS_IIA only for `EMDN_CONSUMER_LEAN_CATS` = M/Y/T/A/N** (dressings/aids/incontinence/ostomy/TENS — IIa carries more genuinely-professional devices, so the rest stay review). This answers *"may it be sold to a consumer"* (MepV default = yes unless restricted), NOT *"who is it intended for"* — a restriction-not-found presumption; the broad Class I sweep does catch a few professional-context items (dental mixing tips, OP-fixation bands) flagged low/verify; else review/low with an `EMDN_PUBLIC_LEAN_CATS` = Y/N (orthoses/TENS) lean note. Measured on 599,806 rows (13.11.2026 corpus after a full `--triage`, 114,084 MiGeL-listed rows, EMDN Z+A+Q01 rules active): professional 367,166 (61.2% — +31,901 on 16.10. from the Q01 dental rule; Aspen Surgical registered 5,855 surgical rows on 16.09., all professional/low via EMDN) · public 211,470 (121 IVD-self-test high + 114,084 MiGeL medium + 97,265 low, 35.3% — 9,405 limb-prosthesis rows moved low → medium on 10.11. with the EMDN layer — 740 Trulife breast forms moved low → medium on 07.11. with the ch. 24 pin — public/low grew by ~15,200 on 03.11. with Bauerfeind's unpinned class-1 stockings — public/low jumped by ~16,300 on 12.10. when Schein filed 12,787 then-unpinned "MyGeneration" shoes and thuasne 3,576 mostly compression-stocking rows, and gave ~12,800 back to public/medium on 13.10. when the MyGeneration pin took effect (21,594 rows with that day's 8,807 new ones) — public/medium jumped by ~12,000 on 08.10. when the Schein LucRo shoe pin took effect and by another ~6,600 on 09.10. as Schein kept filing — public/low grew by ~5,100 on 11.09. and again by ~3,700 on 17.09. when SBO Hearing A/S registered 4,000 and then 3,685 hearing aids under EMDN Y2145, all Class I/IIa consumer-lean and correctly "sellable"; hearing aids are IV/AHV-financed, not MiGeL, so they never reach public/medium) · review 21,170 (3.5% — +3,700 on 04.11. from the Zimmer / Biomet / Wright implant catalogues — fell from 11.6 % on 16.10. when the Q01 dental rule absorbed the orthodontic catalogues of Ormco (6,164 rows on 08.09.) and American Orthodontics (7,048 on 16.10.) that had parked there as Class IIa without a covering category — the higher-risk tail: Class IIa non-consumer-EMDN, Class IIb, IVD, SPP). Both category additions behave identically and are worth trusting for that reason: each moved rows into professional/low and **nothing else**, with no tier above TIER 6 touched (public/medium, professional/high and professional/medium bit-identical before and after). Z moved 16,391 rows (9,783 from review/low, 6,608 from public/low); A moved 2,875 (2,776 from public/low, 99 from review/low), both counts predicted exactly in SQL from the tier ordering before the code was written. The largest cluster Z corrects: 1,632 `Z12010701` FIXED SCIALYTIC LAMPS — operating-theatre lights the TIER-7 Class-I sweep had been calling "sellable to consumers" — plus endoscopy instruments (252), multi-parameter monitors (313), ECG/ultrasound/polysomnography accessories. For A: low-pressure extension lines (867), flow regulators (419), infusion pump controllers (89), stopcocks (79), intraoperative suction containers (85), blood-gas syringes (66), contrast-media injector syringes (35), biopsy and venipuncture needles. Risk class & EMDN proven NOT to identify public; free text yields <1% reliable signal (`laien`/`selbstanwendung`/`home use`/… combined hit <100 rows corpus-wide) — MiGeL is the strongest derivable lay-use signal, but MiGeL (a *reimbursement* list) ⊊ sellable-to-consumers: verified the official BAG MiGeL (per 01.01.2026, 884 positions) has ZERO mattress positions, so anti-decubitus/Pflege mattresses (CH: covered via Pflege/Spitex Art. 25a KVG, not MiGeL) can never match and are handled by `PUBLIC_EMDN_CODES` instead. Integrated into `--details`/`--details-update` (`classify()` appends the 3 columns during fetch; MiGeL map loaded once per run, and the `--migel` daily hook writes today's MiGeL DB before `update_details()` so new rows see fresh matches); `--triage` re-classifies an existing DB in place (ADD COLUMN + UPDATE, idempotent, re-parses `rawJson` + re-joins MiGeL so it stays the single source of truth). Every `review` row (and any listed product) must be verified against the manufacturer IFU/Zweckbestimmung + MepV Abgabe rules before use.
- `src/export.rs` — `write_csv` (UTF-8 BOM), `write_sqlite[_table]` (identifier-quoted SQL), `output_csv`/`output_db`/`output_pdf` path helpers. Also owns the **single** "newest dated DB" lookup: `dated_db_key(name, prefix)` turns the `DD.MM.YYYY` stamp into a `YYYYMMDD` sort key and `find_latest_dated_db(dir, prefix)` picks the max (mtime only breaks ties). Neither lexical nor mtime order is safe here — `udi_details_01.09.2026.db` sorts *before* `udi_details_28.08.2026.db`, and mtime flips the moment a DB is copied, restored or rsynced (`update_details` carries the previous day's file forward). `details::find_latest_db` and `status_pdf::find_prev_db` both route through it; `migel_stats::find_latest_dbs` uses `dated_db_key` directly so the undated (current-scheme) `swissdamed_migel.db` outranks every legacy dated one. `sigvaris_shop::find_latest_db` keeps its own copy of the same logic because it also has to exclude the `_partial.db` checkpoint.
- `src/status_pdf.rs` — `--status-pdf` mode: one-page A4 status sheet (triage distribution + method + key findings) plus a second **nomenclature legend page** (EMDN/MDR/IVDR/MiGeL/KLV/MepV/… with clickable source links). Pure Rust via `genpdf` (writes through `printpdf`), DejaVu Sans embedded from `assets/fonts/` (single-binary preserved; sheet uses no italics so italic slots reuse upright faces). Reads the live distribution from the newest `udi_details_*.db` (`details::find_latest_db`) and writes `pdf/swissdamed_triage_status_DD.MM.YYYY.pdf` (`export::output_pdf`). When run from a checkout, `mirror_into_repo()` then copies the sheet into the repo's `pdf/`, deletes the previous day's, and points the README's "latest sheet" link at it — the same service `migel_stats::generate` performs for the stats PNG. This used to be hand-maintained and went dead on 02.09.2026 when the daily commit mirrored the new sheet but left the link on the deleted one. `rewrite_readme_link()` swaps only the `[**<name>.pdf**](pdf/<name>.pdf)` fragment rather than matching the surrounding sentence (the PNG link is a whole line and can be matched as one; this one sits mid-prose, so keying on the prose would break on any rewording), returns `None` when the link is already current so a same-day re-run leaves the tree clean, and refuses a span over 200 chars so a stray opening fragment cannot swallow paragraphs. Four tests pin exactly those cases. **All numbers are pulled dynamically — never hardcode a figure in the prose.** Each distribution share also shows its day-over-day change: `find_prev_db()` locates the DB immediately preceding the latest by the DD.MM.YYYY date in the filename (robust against carry-forward mtimes), `delta_pp()` computes the signed percentage-point delta of the share to two decimals (`±0.00 Pp.` when it rounds to zero, so no bare `−0.00`; two decimals so sub-0.1-Pp. daily moves in a growing corpus stay visible instead of collapsing to zero), and `metric()` renders it as a separate small (7 pt, ≈50 % of the 10 pt value) muted run — deliberately NOT 8 pt, which is the `LINK_FONT_SIZE` sentinel. The "review sank from X to Y" bullet likewise derives both percentages live (`before = review + public/medium + public/low`, `after = review`). genpdf 0.2 has no native hyperlinks, so `add_links()` overlays `Link` annotations via `lopdf` 0.34: the legend URL lines are the ONLY text set at `LINK_FONT_SIZE`=8, so the post-process finds them and maps them in document order to `LEGEND`'s URLs (order = source of truth; count-mismatch warns, non-fatal). No download.
- `src/diff.rs` — `diff_csv_files` (compares two CSVs by `udiDiCode`).
- `src/gdrive.rs` — Google API access via the project service account, both directions. **Write:** JWT-signed Drive upload + Gmail send (RFC 2047 subject encoding). **Read** (`--gdrive-download`, `--gmail-search`, `--gmail-attachments`, `--gmail-read` for a whole thread as text) and **draft** (`--gmail-draft body.txt --reply-to <id> [--to] [--subject] [--cc] [--update-draft <draft_id>]`, `gmail.compose` scope; a reply derives To/Subject/threadId/In-Reply-To from the original message): pull a partner's spreadsheet out of Drive or find the mail that carried it — these were throwaway Python during the Galaxus GTIN work and live here so a repeat run is a command, not a rebuild. All four share `extract_pem_from_p12` + `get_google_access_token`; reading a Workspace mailbox additionally needs `--gdrive-sub` (domain-wide delegation) because a service account has no mailbox of its own. Gotchas pinned by tests: attachment filenames come from the sender and are sanitised so a `../` cannot escape `--out`; Gmail nests parts arbitrarily deep so the payload tree is walked recursively (top-level-only misses forwarded attachments); the Drive read path is `alt=media` raw bytes, which native Google Docs/Sheets do not have (rejected with an explanation rather than a 400). The HTTP client uses a 900 s timeout — reqwest's default cuts a 19 MB download off mid-body and surfaces only as "error decoding response body". Note `Config::load()` reads `~/swissdamed2sqlite/config.toml` (app data dir), NOT the repo copy.
- `src/migel.rs` — Aho-Corasick MiGeL matching engine (shared with fb2sqlite).
- `src/migel_stats.rs` — pure-Rust stats PNG renderer via `plotters` (`generate`, `find_latest_dbs`, `read_stats`).
- `src/sigvaris_shop.rs` — scrapes `shop.sigvaris.com` Shopify endpoints, derives MiGeL codes per GTIN, persists to `db/sigvaris_shop_DD.MM.YYYY.db`. Exposes `find_latest_db` + `load_overrides` consumed by `run_migel` as a GTIN→MiGeL precedence layer.

**Layer 1 — GTIN overrides** (`src/sigvaris_shop.rs`): scrapes `shop.sigvaris.com` Shopify endpoints (~432 products, ~18k variants), derives MiGeL codes per GTIN from `option2` (Kompressionsklasse) + `product_type` (Wadenstrumpf/Schenkelstrumpf/Strumpfhose/Maternity/Armkompressionsstrumpf/Flachstrick/Wraps/Anziehhilfe), then persists to `db/sigvaris_shop_DD.MM.YYYY.db` with table `sigvaris_shop_variants(handle, gtin13, gtin14, sku, title, product_type, klasse, migel_code, migel_reason)`. Trigger via `--sigvaris-shop`; takes ~7 min with 1s throttle, retries on 403. In `run_migel`, `find_latest_db` + `load_overrides` build a `HashMap<gtin, Option<MigelCode>>` consulted before the heuristic matcher: `Some(code)` → assign that code, `None` → explicit skip (BAG Kap.17: Stützstrumpf / Anti-Thrombose / Reisestrumpf / Klasse 1 are NOT Pflichtleistung).

The scraper is **resume-capable**: per-product variants are appended to `db/sigvaris_shop_partial.db` (with a `done_handles` checkpoint table) immediately after each successful fetch. Rerunning `--sigvaris-shop` skips already-processed handles. When an individual fetch fails after retries, the scraper falls back to the cached variants for that handle from the previous finalized DB. The master handle list per run is the union of (newly discovered) ∪ (partial done) ∪ (baseline DB handles), so Cloudflare-blocked discovery doesn't drop known products. A final **80 % baseline floor** rejects partial scrapes: if the final variant count is below 80 % of the previous finalized DB, the partial is preserved and a future `--sigvaris-shop` resumes from it (no destruction of the override DB). `find_latest_db` excludes `sigvaris_shop_partial.db` and sorts by date-from-filename (`DD.MM.YYYY` → `YYYYMMDD`) so a manually restored older DB is honoured even if its mtime is fresher than a junk replacement.
